# 5-6 Summary: MiniCompiler Backend & Semantic Enhancements


## 1. Semantic Analysis Enhancements
We tightened the semantic rules to catch common logical errors before code generation:
- **Missing Return Check**: Non-`void` functions are now verified to ensure every possible execution path ends in a `return` statement.
- **Unreachable Code Detection**: The analyzer now detects and reports code that follows a `return` statement within the same block.

## 2. Sprint 5: x86-64 Code Generation
Implemented a robust backend that translates SSA IR into valid NASM assembly:
- **System V ABI Compliance**: Implemented standard register-based parameter passing (`rdi`, `rsi`, etc.) and return value handling.
- **Stack Management**: Automatic allocation of stack frames with mandatory **16-byte alignment** for ABI compatibility.
- **Runtime Integration**: Created `src/runtime/runtime.asm` to provide basic I/O (`print_int`) and process exit functionality via Linux syscalls.
- **Entry Point**: Added `_start` generation to link the compiler's `main` function to the OS process lifecycle.

## 3. Sprint 6: Control Flow & Logical Optimization
Expanded the language's capabilities to handle complex logic:
- **Branching**: Full support for `if-else`, `while`, and `for` loops using optimized jump logic.
- **Short-Circuit Evaluation**: Implemented "branchy" logic for `&&` and `||` operators, ensuring the second operand is only evaluated when necessary.
- **Relational Operators**: Translation of all comparison operators into `cmp` and `setcc` instruction sequences.

## 4. Architectural Refactoring (Modular Codegen)
The monolithic `X86Generator` was refactored into a modular, maintainable structure:
- **`label_manager.rs`**: Centralized label sanitization and formatting.
- **`stack_frame.rs`**: Isolated stack offset calculations and alignment logic.
- **`expression_generator.rs`**: Dedicated logic for arithmetic and comparison emission.
- **`control_flow_generator.rs`**: Specialized jump and branch generation.

## 5. Performance Optimizations
Added a **Peephole Optimizer** pass to the backend:
- **Redundant Move Elimination**: Removes unnecessary "store-then-load" sequences (e.g., `mov [rbp-8], rax` followed by `mov rax, [rbp-8]`).
- **Instruction Selection**: 
    - Replaces `mov rax, 0` with the faster `xor eax, eax`.
    - Replaces `add rax, 1` with `inc rax`.

## 6. Documentation & Testing
- **User Guides**: Updated `README.md` and `noob_guide.md` with compilation instructions.
- **CLI Reference**: Documented the new `compile` command and assembly workflow.
- **Automated Tests**: Added `tests/codegen_tests.rs` and verified the entire pipeline with **104 passing tests**.

## Technical Q&A & Implementation Details

### 1. SSA IR and $\phi$-functions
**Q: Does your IR include $\phi$-nodes? If yes, how are they lowered?**  
**A:** Yes, the IR is in full SSA form and includes $\phi$-nodes generated by the `SSAConstructor`. For Sprints 5-6, the code generator focus is on lowering standard instructions. $\phi$-nodes are currently "hidden" or ignored during the final assembly emission because our current test cases utilize simple stack-based variables that bypass the need for complex $\phi$-lowering. For a full implementation, we plan to lower $\phi$-nodes into explicit `mov` instructions in predecessor blocks (Edge Splitting) before the codegen phase.

### 2. Unreachable Code Detection
**Q: What about code after infinite loops (`while(true)`) or breaks?**  
**A:** The current unreachable code detection is **syntax-based and local**. It identifies code that immediately follows a `return` statement within the same block. It does not yet perform full Control-Flow Graph (CFG) reachability analysis (e.g., detecting that code after an infinite loop is dead). This is a planned enhancement for the "Advanced Semantic Analysis" phase.

### 3. Entry Point `_start` and Runtime
**Q: Does `_start` properly retrieve `argc`/`argv`?**  
**A:** Currently, `_start` is minimal. It ignores `argc` and `argv` because the current MiniCompiler language specification defines `main` as a parameterless function. We follow the raw Linux ELF64 contract where `rsp` points to `argc`, but we do not yet expose these to the user program. Our runtime avoids libc to stay "bare-metal," using raw syscalls for `print_int` and `exit`.

### 4. Stack Alignment
**Q: How do you handle the 8-byte misalignment after the `call` instruction?**  
**A:** The x86-64 ABI requires `rsp` to be 16-byte aligned *before* a `call`.  
1. At function entry (right after `call`), the stack is 8-byte misaligned (because the return address was pushed).  
2. We immediately `push rbp` (8 bytes), which re-aligns the stack to **16 bytes**.  
3. Our `StackFrame` then ensures that any additional `sub rsp, N` uses an `N` that is a multiple of 16.  
This ensures that when we reach another `call` instruction, the stack is perfectly aligned.

### 5. Peephole Optimization Scope
**Q: Does the redundant move elimination work across basic blocks?**  
**A:** No. The current `PeepholeOptimizer` is a **local, text-based pass**. it only sees a small window of instructions in the final assembly. It does not perform cross-block liveness analysis. It is designed to catch the most frequent "store-then-reload" patterns generated by the stack-based backend within individual basic blocks.
