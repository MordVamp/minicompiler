# Анализ лекции/консультации по разработке компилятора (от 26.05.2026)

Данный документ представляет собой структурированный анализ аудио-транскрипта, в котором обсуждаются ключевые аспекты отладки, тестирования, профилирования компиляторов и организационные моменты защиты проектов.

---

## 1. Отладочная информация (Дебаггинг и DWARF)
Преподаватель подчеркивает важность связи сгенерированного ассемблерного кода с исходным кодом на высокоуровневом языке. 
* **Локации (Locations):** Для поддержки отладки (например, в GDB) необходимо аннотировать ассемблер специальными директивами, указывающими `file_id`, `line` и `column` исходного кода. Это позволяет отладчику "прыгать" по строкам высокоуровневого кода при пошаговом выполнении.
* **Таблица символов:** Продвинутый уровень (на оценку "5") подразумевает выгрузку глобальных и локальных символов в отладчик, чтобы разработчик мог инспектировать значения переменных во время выполнения.

## 2. Пирамида тестирования компилятора
Рассмотрены различные подходы к тестированию пайплайна компилятора:

* **Unit Testing (Юнит-тесты):** Изолированная проверка каждого модуля (Лексер, Парсер, Семантика, IR-генератор, Кодогенератор). Идеальный юнит-тест кодогенератора должен проверять точную последовательность сгенерированного промежуточного (или ассемблерного) представления.
* **Integration Testing (Интеграционные тесты):** Подход "Черного ящика". Исходный код (например, алгоритм сортировки или факториал) прогоняется через весь пайплайн компилятора до исполняемого файла, после чего проверяется результат его работы (exit code или stdout).
* **Differential Testing (Дифференциальное тестирование):** Сравнение поведения программ, скомпилированных вашим компилятором и эталонным (например, GCC). Для этого можно использовать генераторы случайного кода (типа C-Smith), избегая при этом конструкций с Undefined Behavior (UB).
* **Fuzzing (Фаззинг):** Тестирование компилятора на отказоустойчивость путем подачи некорректных случайных данных. Основная цель — убедиться, что компилятор "падает изящно" (revert gracefully), выводя понятные ошибки, а не "вываливает" необработанные исключения. Для AST-деревьев лучше применять грамматический фаззинг (Grammar-aware mutation).
* **Property-based Testing (Тестирование свойств):** Применяется для оптимизатора. Главное свойство (инвариант) любой оптимизации — **она не должна менять наблюдаемое поведение программы**. (Скомпилированный с оптимизацией и без нее код должен выдавать идентичный результат).
* **Mutation Testing (Мутационное тестирование):** Оценка качества покрытия кода тестами. В код компилятора умышленно вносятся ошибки (например, `+` меняется на `-`). Если после этого тесты проходят успешно — значит, эта часть кода ими не покрыта.

## 3. Профилирование производительности (Profiling)
Акцент делается на профилировании **сгенерированного бинарника**, а не самого компилятора (так как компилятор отрабатывает один раз — AOT).

* **Базовые метрики:** Время выполнения (Wall clock time) через утилиту `time`. Это шумная, но самая простая метрика.
* **Аппаратные метрики (`perf`):** Использование профилировщиков (например, Linux `perf stat`) для сбора статистики железа: количество тактов, инструкций (IPC), ошибок предсказания переходов (branch misses).
* **Кэш-промахи (L1 Cache Misses):** Критически важная метрика. Промахи в L1 кэше заставляют процессор лезть в долгую оперативную память, что экспоненциально замедляет выполнение.
* **Поиск "Бутылочных горлышек" (Bottlenecks):** Если 90% времени уходит на логику вычислений — это проблема алгоритма пользователя. Если же время тратится на пролог/эпилог функций (постоянная загрузка и выгрузка переменных из стека) — это проблема неэффективности компилятора (плохой Register Allocation или отсутствие DSE).

## 4. Организация защиты проектов (Оргмоменты)
* Защита назначена на вторник (ориентировочно в 12:40 - 12:50).
* Допускается заочная сдача через видео-демонстрацию (Screencast), где в кадре видно лицо разработчика и процесс работы компилятора.
* **Дистрибуция:** От студента ожидается готовый, упакованный дистрибутив компилятора (например, бинарник `.exe` для Windows или скрипт-инсталлятор), который легко развернуть на стенде проверяющего без долгих настроек окружения.
* **Платформозависимость:** Преподаватель предупреждает о проблемах с интероперабельностью. Несмотря на то, что ассемблер x86-64 универсален, вызов внешних C-функций (printf, scanf) требует линковки с `libc`. На Windows это потребует установки MinGW (или аналогов), в отличие от Linux, где это работает из коробки.
