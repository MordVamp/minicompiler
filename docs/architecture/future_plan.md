# Планы по улучшению генератора кода (Бэкенд)

Этот документ описывает известные архитектурные неэффективности и минорные проблемы текущей реализации x86-64 кодогенератора, которые были выявлены в ходе тестирования. 
Данные пункты не влияют на корректность выполнения программ, но существенно сказываются на производительности и размере бинарного файла. Их планируется исправить в рамках внедрения фазы продвинутой оптимизации.

## Архитектурные неэффективности (Требует рефакторинга / Оптимизатора)

### 1. Избыточное выделение памяти на стеке
Сейчас компилятор применяет стратегию "наивной" аллокации (Naive Stack Allocation). 
Для каждой переменной, аргумента и промежуточного результата вычисления жестко резервируется слот на стеке в прологе (`sub rsp, X`), даже если переменной можно было обойтись вообще без памяти. 
Например, для функции, где достаточно 8 байт, может быть выделено 32 байта.
**Решение:** Внедрение алгоритма распределения регистров (Register Allocation, например Linear Scan).

### 2. Дублирование значений и лишние операции сохранения (mov)
Кодогенератор пропускает каждую операцию через память: загружает операнд со стека в регистр (`mov rax, [rbp-8]`), выполняет вычисление, а затем сохраняет результат обратно на стек (`mov [rbp-16], rax`), даже если результат сразу после этого используется в следующей инструкции.
Кроме того, аргументы функции, которые уже находятся в регистрах (`rdi`, `rsi`), принудительно выгружаются в стек перед началом выполнения тела функции.
**Решение:** 
- Улучшить логику трансляции выражений (вычислять "цепочки" операций в регистрах).
- Расширить `PeepholeOptimizer`, чтобы он выявлял и вырезал избыточные пары инструкций сохранения и загрузки.

### 3. Отсутствие оптимизаций базовых паттернов вычислений
Некоторые операции могут быть реализованы гораздо короче. Например, возведение в квадрат сейчас занимает 9 инструкций с обращениями к памяти, хотя при наличии распределителя регистров это может быть `mov rax, rdi`, `imul rax, rax`, `ret` (3 инструкции).
**Решение:** Оптимизация на уровне IR (Constant Folding, Copy Propagation) и улучшение трансляции специфических узлов AST.

## Косметические недочеты (Незначительный приоритет)

### 4. Неправильный порядок секций и мусор в `extern`
Кодогенератор жестко (хардкодом) объявляет внешние функции `extern print_int`, `extern read_int`, `extern exit` в начале выходного `.asm` файла, даже если исходная программа их не использует. Это не вызывает ошибок компиляции (линкер просто игнорирует неиспользуемые объявления), но засоряет исходный код ассемблера.
**Решение:** Собирать список используемых внешних функций на этапе семантического анализа и генерировать `extern` только для них.
